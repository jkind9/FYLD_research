# Android SLAM implementations

Primary repositories and documentation checked on 2 October 2026. There are real Android implementations worth studying. The inspected examples cover on-phone monocular tracking, a phone recorder with desktop processing, headset-specific stereo and native ARCore-backed mapping. None establishes a maintained, ready-to-deploy ORB-SLAM3 visual-inertial system with measured accuracy on the available S23 or Redmi Note 11 Pro.

This review complements the [current algorithm comparison](../README.md) and [user-supplied papers](../user_sources/README.md). Runtime figures are author reports, not measurements reproduced here. No APK, SDK or native library was installed.

## Native ARCore as an independent phone route

[ARCore's camera API](https://developers.google.com/ar/reference/java/com/google/ar/core/Camera) exposes an estimated pose and [tracking state](https://developers.google.com/ar/reference/java/com/google/ar/core/TrackingState). These can feed the reconstruction experiment after axes, transform direction, timestamps and map-origin behavior have been checked. They remain estimated poses, not ground truth. RTAB-Map demonstrates a concrete native bridge.

[Recording and Playback](https://developers.google.com/ar/develop/recording-and-playback), documentation updated 4 September 2026, stores camera imagery and inertial/API data in MP4 and supports replay as a session input. The default tracking CPU image is 640×480; a higher-resolution CPU stream needs explicit camera configuration and can affect performance. The recorded depth visualization is for preview, not a metric-depth export. Replaying a recording through ARCore does not automatically give an ORB-compatible calibrated dataset; verify extracted calibration and sensor timestamps separately.

This route is useful for capture and reconstruction controls while the open tracker is evaluated on recorded inputs. Device support, depth availability and terms must be checked for exact model/firmware. Native pose estimation, custom ORB tracking and dense mapping should be reported separately.

## Suggested implementation comparison

| Route | Independent first check | Main unresolved question |
| --- | --- | --- |
| Phone recorder → desktop ORB-SLAM3 | Retain raw video/IMU, calibrate, convert explicitly and compare estimated trajectory against independent reference | Are timing, initialization and scale reliable on actual handset captures? |
| Native phone ORB library | Modernize a small camera/JNI replay path, then compare the same saved inputs with upstream desktop output | Can current Android hardware sustain useful tracking within thermal/memory limits? |
| Phone VIO port | Validate image/IMU clock relationship and extrinsics before initialization tests | Does an old port reproduce the upstream estimator correctly after toolchain updates? |
| ARCore pose/depth → fusion | Export pose/status/calibration and actual depth with valid masks; test fusion independently | Does native tracking/depth provide accurate dimensions and coverage in target scenes? |
| Phone tracking → server map updates | First compare recorded observations without a network; then add controlled transfer/disconnection | What corrections cross the boundary, and how are old poses/geometry updated? |

The evidence favors starting with recording and matched-input desktop comparison before selecting an Android port. This preserves independent tests and makes later phone failures attributable to capture, native integration or tracking. Python can run evaluation and conversion; camera access and the C++ tracker can use a native bridge. These are candidate next steps, not completed builds or selected numeric acceptance limits.
